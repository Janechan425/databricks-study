Domain 1
Concepts to connect

Concepts to connect

• Lakehouse combines data lake flexibility with warehouse management. Medallion layers define data refinement, not file formats.

• Unity Catalog is governance / namespace: catalog.schema.table. Volume is a governed logical place for non-tabular files in cloud storage; it is not a disk drive or a database storage quota.

• Compute: all-purpose/interactive vs jobs vs serverless; SQL warehouses serve SQL workloads. Photon accelerates supported queries with a vectorized execution engine; DBUs measure Databricks compute consumption.

• Delta Lake is a table format implemented with Parquet files and a _delta_log transaction log. A Delta table is not the same thing as an incremental load. Delta supports ACID, MERGE, table history and time travel.

• Managed vs external = who controls storage lifecycle; Delta vs Parquet = storage format; Bronze/Silver/Gold = architectural layer; full vs incremental = ingestion method. These are separate axes.

• Time travel requires transaction history and data files. VACUUM can remove obsolete files, restricting recoverable versions.

Quick SQL examples

CREATE TABLE main.bronze.events (id BIGINT, payload STRING) USING DELTA;
DESCRIBE HISTORY main.bronze.events;
SELECT * FROM main.bronze.events VERSION AS OF 0;

Exam traps

• A Delta table can receive full overwrites or incremental MERGEs; Delta does not by itself initiate incremental ingestion.

• A temporary view is session-scoped; a persistent view stores a query, not physical result rows.

• A shallow clone refers to source data files, whereas a deep clone copies them; neither is an excuse to ignore retention.

• delta.logRetentionDuration differs from delta.deletedFileRetentionDuration.

Domain 1
Unity Catalog (UC) vs DBFS

Unity Catalog (UC) vs DBFS

Unity Catalog (UC) is Databricks' centralized governance layer for data and AI assets. Tables use the three-level namespace catalog.schema.table. Catalogs and schemas are logical governance objects, not filesystem mount paths.

DBFS stands for Databricks File System. Legacy DBFS mounts provided access to cloud storage through mounted paths. For new governed workloads, prefer Unity Catalog external locations and volumes instead of legacy DBFS mounts.

A common organization is to use catalogs for environments (dev, prod) and schemas for layers (bronze, silver, gold), although conventions vary.

Shallow clone vs deep clone

Shallow clone vs deep clone

A shallow clone creates a new Delta table with its own metadata and transaction history but references existing data files from the source. It is fast and storage-efficient, but it is not a fully independent backup.

A deep clone copies data files as well as the necessary metadata, making it more independent of the source.

What if the source table deletes rows?

A SQL DELETE on a Delta table generally records removals in the Delta transaction log; existing Parquet files may still be physically present. A shallow clone can continue reading referenced files while those files remain available. However, if source files are later physically removed (for example, by VACUUM), the shallow clone may fail to read them. Do not rely on a shallow clone for long-term backup or data isolation.

What does “metadata” mean in Delta Lake?

What does “metadata” mean in Delta Lake?

Metadata is information about the table and its data, rather than the actual row contents. Examples include:

• Table schema and column definitions

• Table properties and protocol information

• Delta transaction-log actions describing active data files

• Partition information and file statistics

• Transaction history and commit information

A shallow clone has its own Delta log and table identity, but can point to the source table's physical data files.

Delta retention settings

Delta retention settings

delta.logRetentionDuration controls how long Delta transaction-log history is retained for cleanup, with a default of 30 days. It does not guarantee that every old table version can be queried for 30 days: time travel also depends on whether the required data files still exist.

ALTER TABLE employees
SET TBLPROPERTIES (
  'delta.logRetentionDuration' = 'interval 30 days'
);

Use the documented interval 30 days format. interval means a duration or time interval, not a scheduled action.

Distinguish this from delta.deletedFileRetentionDuration, which controls retention of logically removed data files relevant to VACUUM.

Domain 2
1. What is schema inference?

1. What is schema inference?

Schema inference discovers the initial column names and data types from input files. Auto Loader samples up to 50 GB or 1,000 files by default (whichever threshold is reached first) and persists its inferred schema in cloudFiles.schemaLocation.

For JSON, CSV, and XML, Auto Loader normally infers columns as STRING to avoid unexpected type mismatches; cloudFiles.inferColumnTypes=true asks it to infer specific types. Parquet and Avro have embedded type information.

Example input: {"id":101,"active":true}

• Default JSON Auto Loader inference: id STRING, active STRING

• With inferColumnTypes=true: typically id BIGINT, active BOOLEAN

Inference determines the initial schema; evolution handles later schema changes.

5. What are JDBC and REST?

5. What are JDBC and REST?

• JDBC (Java Database Connectivity): standard database-access API. A JDBC driver uses a database-specific wire protocol (e.g., PostgreSQL protocol or SQL Server TDS).

• REST (Representational State Transfer): an API architectural style, typically implemented over HTTP/HTTPS; REST endpoints often return JSON.

• Neither JDBC nor REST is itself the low-level network protocol.

9. What does explode() do with nested JSON?

A JSON object becomes a Spark struct and a JSON list becomes an array when read with a typed schema. Use dot paths for struct fields and explode() for array elements.

Auto Loader vs Job triggers vs compute

• Auto Loader = incremental cloud-file discovery/ingestion, via spark.readStream.format("cloudFiles").

• Scheduled trigger = run a job at a specified time; possible empty runs.

• File arrival trigger = start a job when qualifying files arrive in a monitored location; often avoids empty scheduled runs.

• Continuous job trigger = keep the job running for near-continuous processing; not a synonym for Auto Loader.

• availableNow=True = Structured Streaming processes currently available input and then terminates; useful inside a triggered job.

• Serverless Jobs compute = resources on which the task runs, not an ingestion method.

Example flow: *files arrive in a UC Volume → file arrival trigger starts a Lakeflow Job → a notebook on serverless Jobs compute uses Auto Loader → checkpoint identifies unprocessed input → Bronze Delta table.*

Delta streaming UPDATE/DELETE vs schema evolution (Q9)

A default append-only Delta streaming source read can fail when upstream Delta transactions rewrite/update/delete existing records.

• If downstream does not need updates: spark.readStream.option("skipChangeCommits", "true").table("main.bronze.customers"); changed commits are skipped, not replayed as new values.

• If downstream must apply updates/deletes: use Change Data Feed (CDF) / CDC-aware processing, or an AUTO CDC flow into a target streaming table with keys and sequencing.

• Schema evolution (rescue, addNewColumns) concerns changing columns/fields; CDC concerns updating existing rows.

• A target streaming table is *not categorically immutable*: managed CDC processing can maintain current-state data (SCD Type 1).

JSON STRING vs STRUCT/ARRAY (Q12 clarification)

For a column raw STRING containing {"line_items":[{"sku":"A1"},{"sku":"B7"}]}:

Event time, processing time, and watermarks (Q8)

• Event time: timestamp embedded in the record, when the business event occurred.

• Processing time: when Spark processes the record. A record with event time 10:05 may arrive at 10:18.

• Watermark: withWatermark("event_time", "10 minutes") declares a threshold for late event-time data in stateful streaming operations (e.g., windowed aggregation). Roughly, the watermark advances with the maximum observed event time minus 10 minutes; it is not current wall-clock time minus 10 minutes.

• Not a buffer: Spark can aggregate records as they arrive; it does not hold all data for exactly 10 minutes before writing. Watermarks help bound state and eventually finalize/evict old windows. Exact late-record handling depends on micro-batch progress and output mode.

• Not Delta retention: watermark does not delete old rows from the Delta destination table; Delta retention and VACUUM are separate concerns.

Example: a 10:00–10:10 event-time window receives a 10:05 event at processing time 10:06. It can be aggregated immediately. A delayed 10:07 event may still update the window while its state is retained. Once the watermark has advanced past the window end and the state is evicted, later arrivals for that window may be dropped.

Exam trap: 10 minutes means an allowed lateness threshold relative to observed event time, not a fixed 10-minute wait, not 10-minute history filtering, and not automatic deletion of Delta rows. The phrase “10 minutes after the window closes” is a simplification, not a wall-clock guarantee.

Lazy transformations vs actions

Lazy transformations vs actions

• Transformations: select, filter, withColumn, join, groupBy, limit construct a logical plan.

• Actions: show, count, collect, first, and writing trigger execution.

• collect() returns *all* matching rows to driver memory, risking driver OOM. Use show(5) or take(5) for inspection; limit(5) alone is still lazy.

Window functions and filtering

7. Forward fill: carry the latest non-NULL value forward

7. Forward fill: carry the latest non-NULL value forward

Example sorted salaries [80000, NULL, NULL, 95000, NULL] become [80000, 80000, 80000, 95000, 95000].

from pyspark.sql.window import Window

w = (Window.partitionBy("employee_id")
    .orderBy("effective_date", "record_id")
    .rowsBetween(Window.unboundedPreceding, Window.currentRow))

df_forward = salary_history.withColumn(
    "salary_filled",
    F.last("salary", ignorenulls=True).over(w)
)

partitionBy ensures one employee's salary does not fill another's. orderBy needs a deterministic tie-breaker; the frame starts at the earliest row in that employee's group and ends at the current row. ignorenulls=True skips NULL. SELECT employee_id, effective_date,
       LAST_VALUE(salary, TRUE) OVER (
           PARTITION BY employee_id
           ORDER BY effective_date, record_id
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS salary_filled
FROM salary_history;

Domain 3
Broadcast Join vs Sort-Merge Join

Broadcast Join vs Sort-Merge Join

• Broadcast Hash Join: replicate the small side on executors and join locally with large-side partitions; avoids a large-side join shuffle.

• Sort-Merge Join: partition both sides by join key, shuffle as needed, sort within corresponding partitions, then merge.

• SQL /*+ BROADCAST(d) */ asks Spark to broadcast the specified side even above the automatic threshold if the strategy is valid. Broadcasting a large side can cause OOM.

• The term honoured means *respected / followed* (hint accepted).

Domain 3
AQE = Adaptive Query Execution

AQE = Adaptive Query Execution

AQE observes runtime shuffle statistics and can:

1. Coalesce several too-small shuffle partitions into fewer task units, lowering scheduling overhead.

2. Switch a planned shuffle join to Broadcast Hash Join when runtime statistics show a sufficiently small side and conditions permit.

3. Split skewed join partitions into smaller tasks, sometimes replicating the other join-side partition so all matching keys still join correctly.

AQE normally decides after upstream shuffle stages produce runtime statistics. It does not magically split an already-running slow Task midway through execution.

Domain 3
Why fewer shuffle partitions may hurt

Why fewer shuffle partitions may hurt

For 100 GiB of uniformly shuffled data: 200 partitions average ~0.5 GiB each; 50 partitions average ~2 GiB. Bigger partitions may increase memory spill to disk and Task duration. But increasing partitions does not inherently split one hot grouping key into many partitions.

Domain 3
Salting for aggregation skew

Salting for aggregation skew

Suppose provider_id=101 dominates a GROUP BY provider_id. Introduce a salt 0–3 to divide that logical group:

from pyspark.sql import functions as F

df_salted = df.withColumn("salt", (F.rand() * 4).cast("int"))
partial = (df_salted.groupBy("provider_id", "salt")
    .agg(F.sum("amount").alias("partial_amount")))
result = (partial.groupBy("provider_id")
    .agg(F.sum("partial_amount").alias("total_amount")))

Think divide → parallel partial sums → combine. The final SUM is unchanged. Salt values may hash into the same physical partition; even salting is not a guarantee of perfect balance. Spark already performs map-side partial aggregation, so benchmark before using manual salting.

For skewed joins, salting requires both sides to match on (key, salt), often duplicating matching rows on the smaller side; consider broadcast or AQE first.

Array function distinctions (related clarification)

• flatten(array_of_arrays): concatenate one level of nested arrays, e.g. [[1,2],[3,4]] → [1,2,3,4]; stays one row.

• explode(array): emit one row per outer element, e.g. [[1,2],[3,4]] → two rows, each holding an inner array.

• array_join(array, ','): join a flat array into a STRING, e.g. ['A','B'] → 'A,B'.

• transform(array, x -> expression): apply a lambda to each element, returning an array; it does not inherently flatten or explode. Output element types/depth may change depending on the lambda.

CAST vs TRY_CAST; Schema Evolution vs write mode (related clarification)

• CAST('bad' AS INT) errors with ANSI mode enabled; TRY_CAST('bad' AS INT) returns NULL for supported conversions that fail due to malformed values/overflow. Unsupported type combinations can still error.

• .mode('append') adds data; .mode('overwrite') replaces data in the write scope; neither setting by itself means “replace the table schema.”

• .option('mergeSchema','true') enables compatible Delta target schema evolution, typically adding new columns; it is not MERGE INTO (row-level upsert).

• .option('overwriteSchema','true') with overwrite requests replacement of the table schema.

• Auto Loader's cloudFiles.schemaEvolutionMode controls source-file schema discovery on the read side; Delta mergeSchema controls compatible schema changes on the write side. They are separate settings.

4. Control flow: If/else, For each, Run if

Z-order Curve / bit interleaving: interleave binary bits of several coordinates to create a one-dimensional ordering that tends to keep nearby multi-dimensional values together. Rewriting files with this layout improves the locality of file-level min/max statistics, allowing Data Skipping / File Pruning. A Z-curve does not guarantee all nearby points are adjacent. Z-ORDER is physical file layout, not Spark shuffle partition placement, and not a traditional index. Use actual filter patterns; high-cardinality IDs can be useful if frequently filtered.

High Cardinality: many distinct values, e.g. customer_id or email. Low Cardinality: few distinct values, e.g. is_active. There is no universal numerical cutoff. Data Skew is *uneven frequency* across values and is distinct from cardinality. A high-cardinality key may be evenly distributed; a low-cardinality key may be extremely skewed.

Retention: delta.deletedFileRetentionDuration controls deleted-file retention (commonly 7 days default); delta.logRetentionDuration controls log history retention (commonly 30 days default). A successful VACUUM can make historical Time Travel impossible if old versions reference deleted files. Very short retention risks concurrent readers and streaming jobs; default safety checks generally prevent dangerously short retention.

ALTER TABLE main.silver.orders SET TBLPROPERTIES (
  'delta.deletedFileRetentionDuration' = 'interval 30 days'
);

Optimized Writes and Auto Compaction are not the same as running full OPTIMIZE on every write:

ALTER TABLE main.silver.orders SET TBLPROPERTIES (
  'delta.autoOptimize.optimizeWrite' = 'true',
  'delta.autoOptimize.autoCompact' = 'true'
);

File statistics: min/max/null counts support data skipping; optimizer table/column statistics support query planning. delta.dataSkippingNumIndexedCols limits indexed statistics columns on supported tables; it does not create conventional indexes. Bloom filters are probabilistic membership structures (false positives possible); do not memorize the source's delta.bloomFilter.enabled snippet as standard Databricks SQL. Avoid blindly scheduling OPTIMIZE/VACUUM if predictive optimization handles maintenance.

Maintenance: inspect DESCRIBE DETAIL (numFiles, sizeInBytes), Query Profile, actual filter patterns, and query plans; benchmark before/after. Compression: Delta data files are generally Parquet, commonly Snappy; gzip trades CPU for compression, LZ4 favors speed. Never assume uncompressed is fastest end-to-end. The source's delta.detail('employees') and SHOW TABLES EXTENDED employees examples are not valid standard inspection SQL. For partitioned tables, partition predicates can restrict OPTIMIZE; do not confuse that with row-level filtering. Choose maintenance frequency based on workload, not fixed daily/weekly/monthly rules.

CLUSTER BY AUTO automatically selects/evolves keys based on workload and requires Predictive Optimization. Key changes can be beneficial for shifting access patterns, skewed partition layouts and high-cardinality filters. It is not combined with traditional partitioning or ZORDER. Converting a legacy partitioned table requires supported runtime/syntax (source cites DBR 18.1+ REPLACE PARTITIONED BY WITH CLUSTER BY).

Predictive Optimization automates OPTIMIZE + VACUUM + ANALYZE on supported Unity Catalog managed tables (not ordinary external tables or shared-in tables). It may collect statistics during writes. It uses serverless jobs compute with associated billing. The source notes default-on for accounts created from 2024-11-11, with rollout for earlier accounts; check actual workspace settings.

ALTER SCHEMA main.scratch DISABLE PREDICTIVE OPTIMIZATION;

ANALYZE is not empty: it collects statistics for the query optimizer (e.g. table size/cardinality estimates to inform join planning); it does not rewrite files. INHERIT uses the parent catalog/schema setting. If AUTO never chooses keys, check predictive optimization and workload eligibility. If an external table has no predictive optimization history, it is outside the supported managed-table scope. The source lists Premium+, supported region, and suitable runtime/warehouse prerequisites; exact platform requirements evolve.

Broadcast Hash Join duplicates a small dimension table on executors to avoid shuffling the large fact table for that join.

-- orders: ~10M rows; customers: ~1K rows
SELECT /*+ BROADCAST(c) */
    o.order_id, o.amount, c.region
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id;

PySpark equivalent:

from pyspark.sql.functions import broadcast
result = orders.join(broadcast(customers), on="customer_id", how="inner")

View the physical plan with EXPLAIN FORMATTED SELECT ... or result.explain("formatted"); look for BroadcastHashJoin.

• Broadcast ≠ repartitioning both big tables for a Shuffle Join.

• Raising spark.sql.shuffle.partitions changes the number/size of shuffle partitions, not the underlying total join volume.

• CROSS JOIN is not a performance substitute.

• A Broadcast Hint is safe only if a side is small enough to broadcast; the Mock Exam Q35 wording mentions three large tables but assumes some *small dimension* tables exist. Check input sizes/stats before applying the hint.

7.1 Unity Catalog Basics

Unity Catalog (UC) centralizes metadata, authorization, lineage and audit across governed data/AI assets.

Storage credential vs external location: credential = *identity/authorization for cloud storage* (e.g. Azure managed identity); external location = *cloud URL + credential* registered as a UC securable. An external table or external volume uses a path covered by a suitable location; UC permissions and cloud access must both work. /Volumes/... is for files in volumes, not a recommended external-table LOCATION.

UC vs legacy Hive metastore: UC has a three-part namespace, cross-workspace governance, fine-grained permissions, lineage and external-location controls. Legacy Hive often uses a two-part schema.table name with workspace-focused controls. Metastore attachment/automatic UC enablement varies by workspace vintage.

Common issues: (1) table appears in wrong catalog → use fully qualified name or set current catalog/schema; (2) INSUFFICIENT_PERMISSIONS despite SELECT → check parent USE CATALOG and USE SCHEMA; (3) missing UC assets → inspect metastore assignment, workspace bindings and effective permissions rather than assuming one cause.

Exam tips: catalog.schema.object; managed vs external storage; /Volumes/catalog/schema/volume/; credential → external location → external table/volume; USE privileges do not themselves grant SELECT.

With supported adapters and persist_docs, dbt model/column descriptions can populate UC comments. A custom contains_pii=true property does not automatically establish a governed tag or mask.

Common issues: external files survive DROP → delete cloud files separately if appropriate; accidentally dropped managed table → UNDROP within recovery window (7 days default; configurable where supported); LOCATION permission denied → missing CREATE EXTERNAL TABLE; streams fail after SET/UNSET MANAGED → restart.

Exam tips: distinguish storage management from Delta format; managed default/recommended and eligible for predictive optimization; external DROP leaves data; know SET/UNSET MANAGED (14-day rollback); distinguish RESTORE vs UNDROP.

7.3 Access Control and Permissions

Principals: user, group (preferred for people), service principal (production Jobs, CI/CD, bundles' run_as). Use backticks around special-character principal names.

Privileges and inheritance: grants on catalog/schema can apply to current and future children. Traversal and reading are different privileges. To read prod.gold.revenue you normally need USE CATALOG + USE SCHEMA + SELECT. Granting USE CATALOG does not automatically grant USE SCHEMA or SELECT, although multiple privilege *types* can be granted at catalog level and inherited.

-- Read one table (least privilege)
GRANT USE CATALOG ON CATALOG prod TO `analysts`;
GRANT USE SCHEMA ON SCHEMA prod.gold TO `analysts`;
GRANT SELECT ON TABLE prod.gold.revenue TO `analysts`;

-- Read every existing and future table/view in Gold:
GRANT SELECT ON SCHEMA prod.gold TO `analysts`;

-- Broad catalog-wide access can be granted, but is often too permissive:
GRANT USE CATALOG, USE SCHEMA, SELECT ON CATALOG prod TO `analysts`;

-- Discover metadata but NOT row data:
GRANT BROWSE ON CATALOG prod TO `all_employees`;

-- Example write and create privileges:
GRANT USE SCHEMA, SELECT, MODIFY, CREATE TABLE ON SCHEMA prod.silver TO `engineers`;

REVOKE SELECT ON TABLE prod.gold.revenue FROM `analysts`;
SHOW GRANTS ON TABLE prod.gold.revenue;
SHOW GRANTS `analysts` ON SCHEMA prod.gold;

GRANT vs REVOKE: GRANT adds; REVOKE removes the grant for a specified principal at a specified level. REVOKE is not a lasting deny override. User can retain access via another group or inherited schema/catalog grant. To revoke access, identify *effective privileges* from all paths. DENY trap: classic DENY SELECT ... is for legacy hive_metastore, not UC SQL access control. UC's ABAC DENY policy (Beta per source) concerns MANAGE ACCESS CONTROL, not a generic DENY SELECT. To fully hide a table, withhold/revoke SELECT (including inherited/group routes); to hide rows/values, use row filters, column masks, dynamic views or ABAC.

Common issues: SELECT granted but USE parent missing; user retains access after REVOKE due to group/ancestor grant; classic DENY errors in UC; legacy privilege spelling (e.g. USAGE, CREATE_TABLE) instead of USE CATALOG, USE SCHEMA, CREATE TABLE.

7.4 Row Filters, Column Masks, Dynamic Views and ABAC

7.4 Row Filters, Column Masks, Dynamic Views and ABAC

Table-level row filter is a SQL UDF returning BOOLEAN. For each candidate row, TRUE keeps row, FALSE/NULL filters it out; the function does not return a row. OR means any eligible group/region condition suffices; AND means both must hold.

CREATE OR REPLACE FUNCTION prod.security.region_filter(region STRING)
RETURNS BOOLEAN
RETURN is_account_group_member('admins')
    OR (is_account_group_member('canada_team') AND region = 'CA')
    OR (is_account_group_member('us_team') AND region = 'US');

ALTER TABLE prod.silver.patients
SET ROW FILTER prod.security.region_filter ON (country);
-- 'country' = actual table column; 'region' = function parameter name.
-- They need not share a name; passed value/type must match.
ALTER TABLE prod.silver.patients DROP ROW FILTER;

Worked truth table: For current user canada_team and row country='CA': admin=FALSE, (CanadaGroup AND CA)=TRUE, (USGroup AND US)=FALSE → FALSE OR TRUE OR FALSE = TRUE, keep row. For same user on country='US', all conditions FALSE → hide row. An admin gets TRUE for all rows. Group membership is user context, while country changes row-by-row. This is platform-enforced, unlike a user-controlled WHERE.

Column mask: SQL UDF returns original or obfuscated column value; return type must match or be castable to the column type. One directly assigned mask per column; may take other columns as input.

CREATE OR REPLACE FUNCTION prod.security.mask_email(email STRING)
RETURNS STRING
RETURN CASE
  WHEN is_account_group_member('privacy_team') THEN email
  ELSE concat('***@', split(email, '@')[1])
END;

ALTER TABLE prod.silver.patients
ALTER COLUMN email SET MASK prod.security.mask_email;

ALTER TABLE prod.silver.patients
ALTER COLUMN email DROP MASK;

Dynamic view saves a SELECT expression that conditionally masks/filters or joins/aggregates; grant SELECT on the view (and parent USE) instead of base table. Views are not themselves directly assigned table-level row filters/masks.

CREATE OR REPLACE VIEW prod.gold.v_patients AS
SELECT patient_id,
       CASE WHEN is_account_group_member('privacy_team')
            THEN email ELSE '***' END AS email,
       country
FROM prod.silver.patients
WHERE is_account_group_member('admins') OR country = 'CA';
GRANT SELECT ON VIEW prod.gold.v_patients TO `analysts`;

ABAC = Attribute-Based Access Control: centrally apply policies to matching governed tags at catalog/schema/table level (metastore-level policies are Beta per source). A tag is object metadata, not a row or an additional column. pii=email consists of tag key pii and configured tag value email; neither equals a column's actual value alice@example.com or the mask output. Governed tags have centrally controlled definitions/allowed values/assignment permissions; a tag alone does not mask anything.

-- Assuming governed tag 'pii' and permitted value 'email' already exist:
ALTER TABLE prod.silver.patients
  ALTER COLUMN email SET TAGS ('pii' = 'email');

CREATE POLICY mask_pii_email
ON SCHEMA prod.silver
COMMENT 'Mask tagged email columns for analysts'
COLUMN MASK prod.security.mask_email
TO `analysts`
EXCEPT `privacy_admins`
FOR TABLES
MATCH COLUMNS has_tag_value('pii','email') AS email
ON COLUMN email;

SHOW EFFECTIVE POLICIES ON TABLE prod.silver.patients;

Policy clauses: WHEN matches tagged tables; MATCH COLUMNS selects tagged columns; ON COLUMN selects the masked column alias; USING COLUMNS passes matched columns to a row-filter UDF. has_tag('region') checks tag presence; has_tag_value('pii','email') checks key/value. A higher-scope policy is controlled by admins at that scope; table owners cannot just remove it.

Example row-filter ABAC (pre-existing BOOLEAN function prod.security.us_only(region STRING)):

CREATE POLICY us_rows_only
ON CATALOG prod
ROW FILTER prod.security.us_only
TO `contractors`
FOR TABLES
WHEN has_tag_value('sensitivity', 'high')
MATCH COLUMNS has_tag('region') AS region
USING COLUMNS (region);

Requirements / limitations from the source guide: table-level filters/masks require supported runtimes (below DBR 12.2 LTS may fail secure with no rows); dedicated compute has additional serverless FGAC/runtime constraints (15.4 LTS+, writes supported at later runtime). Time travel, cloning, OpenSharing and AI Search have restrictions for table-level policies; ABAC exemptions and supported sharing modes can differ. ABAC uses DBR 16.4+ or serverless in the source and requires policy management privileges plus UDF EXECUTE. Check current docs for version-specific support.

Which to choose? Specific table/column → table-level mask/filter. Many tagged datasets → ABAC. Curated transformed subset and no base-table access → dynamic view. Hide all data → do not grant SELECT.

Common issues: masked DECIMAL column with STRING-returning UDF → incompatible type; old runtime returns no rows → upgrade; time travel/clone on directly policy-protected table fails → plan history/security accordingly; table owner cannot drop ABAC mask inherited from schema/catalog → modify higher-level policy with appropriate permission.

Exam tips: Row filter RETURNS BOOLEAN and uses SET ROW FILTER ... ON (column); column mask uses SET MASK and matching return type; is_account_group_member(); ABAC = policy + governed tags; no classic DENY SELECT in UC.

Minimum read path for a specific table: USE CATALOG + USE SCHEMA + SELECT. Investigating a user's *effective access* also requires considering group membership, inherited privileges from schema/catalog and ownership. A direct table grant listing alone does not always tell the whole story.

Classic SQL DENY SELECT is not a general UC alternative to REVOKE. If a user still receives SELECT through a parent object or another group, revoking just the direct table grant will not necessarily block access. For per-row/per-column restrictions, use row filters / column masks or relevant governed policies.

Not the same: SHOW SHARES concerns Delta Sharing shares; it is not the normal command for table privileges.
